Чем наш CargoFlow будет отличаться от всех референсов:
1. **Exception-first дашборд диспетчера** — наверху не «всего рейсов», а то, что требует действия: задержки, проблемы, не принятые рейсы, ожидающие подтверждения.
2. **Водитель работает одним большим пальцем**: один главный экран рейса с одной следующей кнопкой статуса, большие цели нажатия, работает без сети (outbox).
3. **Клиент видит таймлайн, а не чат**: этапы, время, фото, документы; при задержке — новое расчётное время и причина без служебных деталей.
4. **Документы привязаны к этапу**: фото «до загрузки / после загрузки / при выдаче» и накладная лежат там, где были сделаны, а не в общей куче.

## 4. Выбор стека

**Expo (React Native) + Supabase**, не Flutter и не no-code. Причины:
- taste-skill для мобильных существует именно для RN/Expo — главный рычаг против ИИ-слопа.
- Codex / GPT-6.1 Sol сильнее в TypeScript-экосистеме; меньше галлюцинаций по API.
- Expo Go даёт демонстрацию на реальном телефоне за минуту, EAS — APK для защиты.
- Supabase закрывает авторизацию, Postgres, хранилище фото/документов и realtime-обновления статусов одной бесплатной услугой; RLS-политики дают разделение ролей без собственного бэкенда.
- Студент сможет объяснить архитектуру: «приложение → Supabase → таблицы; статусы — это события».

Риски и ответы:
- Сеть на защите может упасть → **demo-mode** на локальных seed-данных, переключатель в настройках.
- Realtime может задержаться → polling раз в 5 с как fallback.
- Push-уведомления требуют EAS/устройство → используем локальные уведомления + in-app центр уведомлений; настоящие push — «дальнейшее развитие».
