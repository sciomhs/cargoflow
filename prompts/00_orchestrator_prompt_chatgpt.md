## Проект
**CargoFlow** — мобильное приложение для логистической компании (грузоперевозки между
городами Казахстана, ~35 машин, 15–30 рейсов в день). Учебный проект, срок 1 месяц, сдаётся
видеороликом 5–7 минут, который оценивает преподаватель (и ИИ-проверка) по 10 критериям:
понимание задачи, полнота приложения, навигация, полный пользовательский сценарий,
интерактивность с данными, соответствие функций задаче, качество интерфейса, дополнительные
возможности, стабильность демонстрации, качество презентации. Каждый 0–10.

Боль заказчика: диспетчер весь день звонит водителям («загрузился? где машина?»), клиент
звонит диспетчеру («где груз?»), накладные и акты теряются в WhatsApp, статусы устаревают,
истории рейса нет, руководитель не видит картину.

Цель приложения: один актуальный статус рейса, который видят все. Водитель меняет статус
одной кнопкой, диспетчер и клиент видят это сразу, документы и фото привязаны к рейсу и этапу.

## Роли
- **Диспетчер** — создаёт заказ (`CF-1845`) и рейс (`R-642`), назначает водителя и машину, видит все рейсы и цифры по статусам, отдельно — проблемы и задержки, подтверждает доставку.
- **Водитель** — видит только свои рейсы, адреса, контакты, груз; последовательно меняет статусы; добавляет фото по этапам, документы; сообщает о проблеме; фиксирует передачу груза получателю.
- **Клиент** — видит свои заказы, таймлайн этапов с временем, плановую/новую дату доставки, фото и документы; подтверждает получение. Не видит служебные комментарии и телефон водителя.
- **Руководитель** — дашборд: рейсов за месяц, завершено, в пути, задерживаются, отменено, среднее время доставки, загрузка по водителям.

## Главный сценарий (должен работать без единой ошибки, его снимаем в ролике)
Диспетчер создаёт заказ CF-1845 (ТОО «СтройКомплект», керамическая плитка, 8 500 кг,
12 паллет, Павлодар ул. Промышленная 18 → Астана ул. Индустриальная 42, загрузка 21 окт,
доставка до 22 окт 15:00) → создаёт рейс R-642 (Руслан Касымов, Volvo FH 777 ABC 14, выезд
21 окт, план 22 окт 13:00) → водитель получает уведомление → принимает рейс → «Прибыл на
загрузку» → фото груза → «Груз загружен» → «В пути» → клиент видит «В пути» и следующий
этап → «Прибыл на выгрузку» → фото при выдаче + накладная №457 + получатель Алексей Смирнов
→ «Груз передан» → клиент «Подтвердить получение» → рейс «Завершён» → у диспетчера полная
история событий с временем.

Дополнительный сценарий: водитель в пути → «Сообщить о проблеме» → Задержка, Закрытие
дороги, ~90 мин, фото → у диспетчера красная карточка во вкладке «Внимание» → он сдвигает
плановую доставку → статус «Задерживается» → клиент видит новое время и причину
«задержка на маршруте».

## Машина статусов рейса (не менять без пометки DECISION NEEDED)
`assigned → accepted → to_pickup → at_pickup → loading → loaded → in_transit → at_delivery →
unloading → handed_over → awaiting_confirmation → delivered → completed`.
Боковые флаги: `delayed`, `problem`; терминальный `cancelled` (только диспетчер, до `loaded`).
`loaded` требует фото `after_load`; `handed_over` требует запись handover + фото `at_delivery`.
Каждый переход — строка в `trip_events` (`from_status`, `to_status`, `actor_id`, `created_at`).
Логика переходов живёт только в `src/domain/statusMachine.ts`; экраны её импортируют.

## Стек (зафиксирован)
Expo (последний стабильный SDK) + Expo Router + TypeScript strict + NativeWind + Reanimated +
Zustand (сессия, настройки, outbox) + TanStack Query (серверные данные) + Supabase (Auth,
Postgres, Storage, Realtime) + expo-sqlite/MMKV для локального кэша + i18n-js + expo-print
для PDF + lucide-react-native + шрифты IBM Plex Sans / IBM Plex Mono.
Одно приложение, четыре роли, корневой навигатор выбирается по роли после входа.
Данные идут через интерфейс `TripRepository` с двумя реализациями: `Supabase…` и `Demo…`
(локальные seed-данные). Переключатель `demoMode` в настройках. На защите включён demo-mode.

Структура: `app/app/(auth|dispatcher|driver|client|manager)/…` — тонкие экраны;
`app/src/{api,demo,domain,outbox,store,ui,features,i18n}` — логика и компоненты.

## Дизайн — ОБЯЗАТЕЛЬНО (критерий 7, и это то, по чему сразу видно ИИ-слоп)
Перед любой UI-задачей загрузи skill `mobile-taste` (или `mobile-nav-plan`,
`mobile-design-system` по типу задачи) из `draftbit/mobile-taste-skill` и следуй его
протоколу: App Read → Nav Read → дилы → только потом код. Файл `MOBILE-DESIGN.md` в корне
`app/` — закон.

Коротко:
- Характер: «дорожный документ». Рабочий инструмент, а не финтех. Спокойно, плотно, честно.
- Фон `#F4F2EE`, поверхность `#FFFFFF`, текст `#1A1917`, линии `#DCD8D0`. **Один акцент** `#1F6F4A` (primary-кнопка, активный таб, текущий этап). Задержка `#B4411F`, ожидание `#8A6D1F`, завершено `#4E7A5F`. Тёмная тема для водителя.
- IBM Plex Sans для текста, **IBM Plex Mono с tabular-nums для номеров, весов, госномеров, времени и денег**. `32 500 ₸`, `22 окт, 14:30`.
- Радиус 6. Списки — строки с разделителем, не стопки карточек. Статус — текст с цветной точкой. Таймлайн — вертикальная линия слева.
- Иконки Lucide 20px. Кнопка водителя «следующий статус» — 64 высотой, во всю ширину, у нижнего края; цели нажатия ≥ 48 (водитель 56).
- Табы: диспетчер 3 (Рейсы · Заказы · Внимание), водитель 2 (Сегодня · История), клиент 2 (Доставки · Уведомления), руководитель без таббара.
- **Запрещено:** градиенты, индиго/фиолетовый и Tailwind `indigo-*`/`violet-*`, 5 табов + плавающая кнопка, стопки белых карточек с тенью, эмодзи вместо иконок, «Привет, {имя}! 👋», радиусы 16+, иллюстрации людей с ноутбуками, lorem ipsum / John Doe / `+7 999…`, центрированные заголовки, одинаковая плотность у водителя и диспетчера.
- Весь текст интерфейса на русском, деньги в ₸, города Казахстана, имена казахстанские.

## Правила кода
- TypeScript strict, без `any`. Типы сущностей — в `src/domain/types.ts`, совпадают со схемой БД.
- Никаких выдуманных API: если нужна таблица или поле, которых нет в `supabase/migrations/`, опиши миграцию в отчёте и остановись.
- Каждая зависимость — только по задаче, с версией в `versions.md`.
- Не реализовывать GPS, карты с маршрутизацией, оплату, 1С, ЭЦП, расчёт стоимости — вне ТЗ.
- Не трогать чужие экраны «заодно». Нашёл проблему — в отчёт.
- `git`: только локальные коммиты `T-XX: …`. **GitHub не создавать, remote не добавлять, push не делать.**

## Протокол работы
1. Получаешь задачу `T-XX` (из `tasks/backlog.md` или сообщением оркестратора).
2. Пишешь 3–6 строк плана: файлы, которые создашь/изменишь, и что станет проверяемо после. Если план требует решения, которого нет в спецификации — пиши `DECISION NEEDED: …` и жди. Иначе — выполняй, не спрашивая.
3. Делаешь. Проверяешь: `npx tsc --noEmit`, `npx expo lint`, запуск в Expo Go/эмуляторе, прогон затронутого куска сценария в demo-mode.
4. Если задача UI — прогоняешь grep-чеклист `tells.md` из mobile-taste-skill и устраняешь попадания.
5. Сдаёшь отчёт строго по шаблону:

```
## T-XX: <название>
Сделано: <3–8 пунктов, что именно работает>
Файлы: <список путей>
Как проверить: <шаги в приложении, 3–6 строк>
Не сделано / риски: <честно>
DECISION NEEDED: <если есть, иначе «нет»>
Коммит: T-XX: …
```

Отчёт — на русском, без «я надеюсь», без общих слов. Код не вставляй в отчёт целиком,
только пути.
